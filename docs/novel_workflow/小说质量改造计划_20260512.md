# 小说工作流质量改造计划

更新时间：2026-05-12

本文档用于承接“阴阳引渡人”案例暴露出的小说工作流质量问题，并作为后续连续实施、上下文压缩恢复和验收核对的唯一执行底稿。除非后续明确更新本计划，否则实施顺序、边界和验收口径均以本文档为准。

## 1. 改造目标

当前小说工作流已经具备：

- 项目创建、Bible、大纲、导演台、正文、审稿、人工审核等完整链路
- continuity facts、plot threads、AI run 审计、质量闸门等生产稳定性能力
- `阴阳引渡人` 前两章真实产出和后续扩写素材，可作为质量基准样例

但本次分析确认，工作流仍存在 3 类关键问题：

1. **派生工件失效不完整**
   - `BIBLE_PATCH_APPLIED`、`OUTLINE_UPDATED`、`PROJECT_TARGET_UPDATED` 后，旧导演台可能仍被保留为当前有效卡片。
   - 典型症状：`阴阳引渡人` 第 3 章 Outline 已重排为“引魂燃灯”，但当前 Director Card 仍沿用旧终章式规划。

2. **创作信息过早压缩**
   - 当前流程从 Bible 直接进入 Outline，缺少“创作母本 / Story Treatment”层。
   - Outline 只保留章节级摘要，难以承载民俗志异、情绪反转、真相分层释放这类作品所需的“场景级递进”。

3. **导演台同时承担创作与合规，注意力过载**
   - Director 同时负责叙事规划、事实审计、质量闸门、伏笔账本、分段计划。
   - 结果是稳定性增强，但“小说感”和节奏设计容易被表单化约束稀释。

本计划优先解决前两类高收益问题，并为第三类问题预留第二阶段改造入口。

## 2. 当前基准案例

### 2.1 项目基准

数据库项目：

```text
title: 阴阳引渡人
genre: 悬疑灵异
audience: 短篇试读读者
style: 节奏快、冲突强、章末留钩子
target_total_chapters: 5
target_words_per_chapter: 4000
```

### 2.2 对照文本

人工协作优质样例：

```text
/Users/warrn/Desktop/志异故事集-红凶.md
```

重点观察它在以下方面的质量：

- 引魂灯、守灯录、过阴阳桥、妹妹宽恕、阿梅与赵权旧情的分层揭露
- 每个信息点都被拆成独立场景，而不是直接浓缩成剧情摘要
- 情绪由惊悚转入悲恸，再转入救赎的层层递进

### 2.3 工作流验收基准

改造完成后，至少要做到：

- 扩写 / 大纲重排后，不会再保留与新上下文冲突的旧 Director Card
- Bible / Outline 能保留“主题母本”和“场景阶梯”，不只输出章节概述
- `阴阳引渡人` 这类强反转项目，不再被迫从“已固化误判事实”里勉强缝补

## 3. 总体实施策略

实施分 4 个阶段，先做最高收益、最低歧义的内容。

### Stage A：派生工件失效与重算

目标：保证上游创作工件变化后，下游导演台不会继续使用旧版本。

#### A1. 规则定义

当以下事件发生时：

- `BIBLE_PATCH_APPLIED`
- `OUTLINE_UPDATED`
- `PROJECT_TARGET_UPDATED`
- 后续若存在 Story Treatment 更新，也纳入同类规则

系统必须识别“受影响的未写章节”，并执行：

1. 旧当前导演台卡片转为过期状态或失效状态
2. 旧导演台关联的未执行正文任务解除绑定或取消
3. 对受影响章节重新创建 `PLAN_CHAPTER_DIRECTOR` 任务
4. 页面展示应能解释“已因上游内容变化进入重新规划”

#### A2. 章节范围

按扩写范围处理：

- `append_only`
  - 只影响新增章节
  - 已有未写章节不强制失效

- `rewrite_unwritten`
  - 从 `current_chapter_no + 1` 开始的未写章节全部纳入失效与重算

- `regenerate_outline`
  - 所有未批准章节纳入失效与重算

#### A3. 涉及文件

预计修改：

#### A4. 验收

必须覆盖以下断言：

1. 应用 Bible patch 后，受影响未写章节旧导演台不再是当前有效卡片
2. 重生成 Outline 后，旧导演台不会继续驱动正文任务
3. 若第 3 章已有旧 READY Director，而 Outline 第 3 章在 patch 后更新，则系统会新建第 3 章 `PLAN_CHAPTER_DIRECTOR`
4. 页面主动作优先提示“等待重新规划 / 重新生成导演台”，不会误导用户直接生成正文

### Stage B：新增 Story Treatment 创作母本层

目标：在 Bible 之前先固化“作品真正的情绪与叙事引擎”，降低后续结构化环节对创作张力的损耗。

#### B1. 新增工件

新增 `novel_story_treatments`，用于保存：

- `theme_core`
- `reader_promise`
- `mystery_stack`
- `reveal_ladder`
- `emotional_arc`
- `protagonist_inner_wound`
- `symbolic_motifs`
- `ending_payoff`
- `quality_notes`
- `raw_payload`

#### B2. 新增任务

新增 job 类型：

```text
GENERATE_STORY_TREATMENT
```

项目创建后链路改为：

```text
PROJECT_CREATED
-> GENERATE_STORY_TREATMENT
-> GENERATE_BIBLE
-> GENERATE_OUTLINE
```

#### B3. 设计原则

- Story Treatment 只负责“小说母本”，不承担结构化事实库和执行排程
- 它要优先保住：
  - 误判与翻转
  - 情绪兑现
  - 关键信息分层释放
  - 主角伤口与主线的因果连接
- 对 `阴阳引渡人`，它应能明确表达：
  - 恐怖外壳，救赎内核
  - 赵权先被误判，后被翻转
  - 妹妹线是男主接灯资格的一部分，不是装饰性背景
  - 引魂灯是人格转化仪式，而非普通道具

#### B5. 验收

1. 新项目创建后先出现 `GENERATE_STORY_TREATMENT`

### Stage C：Outline 升级为章节 + 场景阶梯

目标：避免“剧情摘要型大纲”，让 Outline 直接保留正文生成真正需要的场景推进结构。

#### C1. 新增字段

在 `novel_chapter_outlines` 中新增：

- `scene_beats JSONB NOT NULL DEFAULT '[]'::jsonb`
- 可选：`reader_questions JSONB NOT NULL DEFAULT '[]'::jsonb`

建议 beat 结构：

```json
{
  "beat_no": 1,
  "beat_goal": "",
  "scene_image": "",
  "new_information": "",
  "emotional_shift": "",
  "reader_question": "",
  "do_not_reveal": ""
}
```

#### C2. Prompt 升级

Outline prompt 必须要求：

- 每章给出 4-8 个 `scene_beats`
- 每个 beat 推动一个独立阅读体验，而不是重复概述
- 若章节承担真相揭露，则必须拆开“线索 -> 误判 -> 修正 -> 情绪兑现”
- 对章节情绪峰值，不允许只用一句“揭示真相”概括

#### C3. 下游使用

Director 和 Chapter 生成都应读取：

- 当前章 `scene_beats`
- 当前章需要保留的 `reader_questions`

Director 不再只基于 `summary` 规划，而是对 beat 做压缩与执行调度。

#### C5. 验收

1. Outline parser 能保存 `scene_beats`
2. Outline 展示页能读取但不必须完整外露全部 JSON
3. Director prompt 会携带 `scene_beats`
4. `阴阳引渡人` 第 4 章“死水心结”不再只是“妹妹安慰男主”一句概述，而能拆出多步场景推进
5. 章节生成时能够基于 beat 更稳定地保留情绪节奏

### Stage D：导演台职责拆分预研

目标：为后续把“叙事导演”和“连续性 QA”拆开做准备。

本阶段先不强制全面落地，但要完成：

- 文档化拆分方案
- 明确当前 Director 中哪些字段应留在 Narrative Director
- 哪些字段应迁移到 Continuity QA
- 哪些现有测试需要重构

建议拆法：

```text
Narrative Director
  - chapter_intent
  - causal_chain
  - segment_plan
  - rhythm_plan
  - reveal_control

Continuity QA
  - fact_source_audit
  - cross_chapter_transition_review
  - blocking_issues
  - quality_gate
```

本计划后续执行到 Stage A-C 稳定后，再决定是否立即进入 Stage D。
