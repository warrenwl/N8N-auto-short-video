# 小说工作流 V1 实施计划

更新时间：2026-05-03

本文档用于把 `docs/novel_workflow/整体架构.md` 拆成可执行阶段，避免后续上下文压缩后偏离实现顺序。当前阶段先以“文本连载小说生产线”为目标，不做自动发布、短视频改编、有声书或封面生成。

## 0. 不可改回的核心规则

- `is_current = true` 只表示“当前正式可续写版本”。
- `DRAFT_READY / AI_REVIEWED / NEED_REVIEW / REWRITE_REQUESTED` 全部保持 `is_current = false`。
- 下一章续写只读取 `is_current = true AND status IN ('APPROVED', 'PUBLISHED')` 的前文版本。
- 生成/审稿第 N 章时，continuity facts 只读 `status = 'ACTIVE'` 且 `(chapter_no IS NULL OR chapter_no < N OR source = 'human')`。
- 重写新版本 facts 先写 `PENDING`，人工通过后才变 `ACTIVE`；旧版本 AI facts 同时变 `INACTIVE`。
- 审核动作必须走 `POST /webhook/novel-review-action`，并校验 `chapter_id + review_token`。
- AI 审稿不能直接 `APPROVED`；人工通过才会设置 `APPROVED + is_current = true`。
- 每次人工动作写入 `novel_human_reviews`。
- 每次 GLM 调用写入 `novel_ai_runs`，包含请求、响应、解析结果和耗时。
- n8n 领取任务必须用 `FOR UPDATE SKIP LOCKED`。

## 2. 阶段拆分

### 阶段完成口径

每个阶段都必须满足下面三件事，才允许报告“阶段完成”：

1. 先按 TDD 写出本阶段失败用例、断言 SQL、脚本测试或工作流验收用例。
2. 实现最小代码/SQL/workflow，让测试从失败变为通过。
3. Refactor 清理本阶段实现，不改变已通过行为。
4. 按该阶段覆盖范围跑一遍完整可执行流程，不只做静态检查。
5. 读取执行结果和数据库状态，确认状态机、关键字段和任务队列符合预期。
6. 更新阶段结论文档，并给出阶段完成结论。

阶段完成结论必须包含：

```text
本阶段变更文件
TDD 用例 / 断言
执行链路
验证命令 / 入口
数据库状态核查
验证结果
遗留风险
下一阶段入口
```

阶段结论统一追加到：

```text
docs/novel_workflow/阶段结论.md
```

早期阶段的“完整流程”按当前能力定义：

- Phase 1：数据库级流程，从建表、建函数到用 SQL 手动模拟创建项目、创建候选章节、人工通过函数。
- Phase 2：脚本级流程，用样例输入跑 Code 节点脚本，确认请求构造、JSON 解析、HTML 渲染和审核动作校验可执行。
- Phase 3：工作流 11-13 流程，从浏览器创建项目到第 1 章任务出现。
- Phase 4：工作流 14-15 流程，从第 1 章任务到 `NEED_REVIEW`。
- Phase 5：主闭环流程，从创建项目到第 2 章任务自动出现。
- Phase 6：生产补强流程，覆盖重写、通知和自动恢复。
- Phase 7：真实 GLM smoke test 流程，用外部 GLM 跑短篇 2 章项目，确认 JSON 稳定性、AI 日志、通知可控和失败证据可追踪。
- Phase 8：真实重写 smoke + 调度运行流程，确认真实 `REWRITE_CHAPTER` 可跑通，并把日常队列执行方式写成可复用脚本和运行手册。
