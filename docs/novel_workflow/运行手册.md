# 小说工作流 V1 运行手册

更新时间：2026-05-09

## Phase 8 运行原则

- 真实运行时不要设置 `GLM_API_BASE_URL=http://host.docker.internal:18080/...`，否则会回到本地 mock GLM。
- 明确禁用写法：不要设置 GLM_API_BASE_URL=http://host.docker.internal:18080。
- 真实 GLM Key、模型和公开链接继续从 `.env` 读取。
- Server酱只做提醒，不承载审核动作；真正操作必须回到审核页并提交 `POST /webhook/novel-review-action`。
- smoke test 默认不发送真实微信提醒，使用 `NOVEL_DISABLE_SERVERCHAN=true`。
- `is_current=true` 只代表当前正式可续写版本；候选稿、待审稿和重写稿都不能抢 current。

## 队列跑一轮

推荐用脚本执行 12-19/18 的一轮队列处理：

```bash
scripts/run_novel_queue_once.sh
```

默认行为：

```text
12 GENERATE_BIBLE / GENERATE_BIBLE_PATCH
13 GENERATE_OUTLINE
13B PLAN_CHAPTER_DIRECTOR
14 GENERATE_CHAPTER
15 REVIEW_CHAPTER
17 REWRITE_CHAPTER + NOTIFY_REVIEW
19 REVISE_CHAPTER_BLOCK
18 auto recovery
```

脚本会临时停止 `n8n-video-n8n` 容器，用 n8n CLI 执行工作流，最后通过 `trap` 启动 n8n，避免运行中 n8n 和 CLI 争抢执行锁。

先看命令，不实际执行：

```bash
scripts/run_novel_queue_once.sh --dry-run
```

默认通知禁用：

```text
NOVEL_DISABLE_SERVERCHAN=true
```

如果确认要发送真实 Server酱提醒，再显式运行：

```bash
scripts/run_novel_queue_once.sh --real-notify
```

## 调度建议

MVP 阶段先用外部调度定期执行脚本，不把 12-17 都改成 cron 节点。这样更容易暂停、观察和回滚。

示例 crontab：

```cron
*/10 * * * * cd /Users/warrn/study/N8N && scripts/run_novel_queue_once.sh >> /tmp/novel_queue_once.log 2>&1
```

生产提醒需要真实外发时，再改成：

```cron
*/10 * * * * cd /Users/warrn/study/N8N && scripts/run_novel_queue_once.sh --real-notify >> /tmp/novel_queue_once.log 2>&1
```

## 人工审核入口

审核列表：

```text
http://localhost:5678/webhook/novel-review-list
```

审核详情链接由 17 号 `NOTIFY_REVIEW` 写入 job payload，形如：

```text
/webhook/novel-review-detail?chapter_id=...&review_token=...
```

审核动作只允许：

```text
POST /webhook/novel-review-action
POST /webhook/novel-review-block-revise
POST /webhook/novel-review-block-apply
```

常见动作：

```text
approve
request_rewrite
reject
```

不要新增 GET 审核动作链接。
局部修订只生成建议，应用时会创建新的待审候选稿，但不会自动进入智能审稿，方便同一章连续处理多处细节。完成本轮局部修改后，可在审核详情右侧点击“重新审稿”主动触发智能审稿，或确认无误后直接通过。审核详情页会保存选区偏移和前后锚点；如果同一段原文在正文中出现多次且无法定位，会返回“锚点不唯一”，要求重新选择。建议返回后页面展示原文/建议 diff，默认只读，点击“修改后应用”才进入编辑态。

审核详情页支持双击正文段落直接改稿。行内保存会走 `decision=save_only`，创建新的待审候选稿并停留在人工审核态，不会自动创建 `REVIEW_CHAPTER`；整章改完后再手动“重新审稿”或直接通过。

## Phase 9 可观测性

16 号审核中心会在列表和详情页展示一组运行观察字段，方便人工审核时直接看到候选稿的上下文：

- `AI调用`：来自 `novel_ai_runs`，展示模型、提示词版本、`duration_ms`、成功状态和错误。
- `任务状态`：来自 `novel_generation_jobs`，展示章节最近一次任务类型、状态、尝试次数和错误。
- `通知状态`：来自最新 `NOTIFY_REVIEW` job 的 payload，展示 `remind_status` 和审核详情链接。
- `事实库`：来自 `novel_continuity_facts`，展示当前候选稿绑定的 `PENDING`、`ACTIVE`、`INACTIVE` facts 数量。
- `人工记录`：来自 `novel_human_reviews`，展示最近人工动作、意见和操作者。

页面入口保持不变：

```text
/webhook/novel-review-list
/webhook/novel-review-detail?chapter_id=...&review_token=...
```

如果页面上某个字段为空，优先用下面的 SQL 判断是“尚未产生记录”还是“工作流未写入”：

```sql
SELECT run_type, model, prompt_version, success, duration_ms, error_message, created_at
FROM novel_ai_runs
WHERE chapter_id = '<chapter_id>'
ORDER BY created_at DESC;

SELECT job_type, status, attempt_count, error_message, payload, updated_at
FROM novel_generation_jobs
WHERE chapter_id = '<chapter_id>'
ORDER BY updated_at DESC, created_at DESC;

SELECT status, source, fact_type, fact_key, fact_value, created_at
FROM novel_continuity_facts
WHERE chapter_id = '<chapter_id>'
ORDER BY created_at DESC;

SELECT action, reviewer, comment, created_at
FROM novel_human_reviews
WHERE chapter_id = '<chapter_id>'
ORDER BY created_at DESC;
```

注意：Phase 9 只增强审核中心展示，不改变章节状态机。候选稿仍然必须保持 `is_current=false`，人工通过后才进入 `APPROVED + is_current=true`。

## Phase 10 只读队列状态页

工作台入口：

```text
/webhook/novel-center
```

工作台只展示当前建议操作、待办总览、需要处理的项目和创建项目入口。

项目列表入口：

```text
/webhook/novel-project-list
```

项目列表会展示项目级观察信息：

- 项目状态、章节进度、已批准章节数。
- 待处理、运行中、失败任务数量。
- 最近任务和最近模型调用。
- 待审章节入口、项目队列入口、运行日报入口和可展开的项目概览。

从项目列表点击“看队列”会进入带 `project_id` 的只读队列页，例如：

```text
/webhook/novel-queue-status?project_id=...
```

该筛选只影响页面显示，不会执行重试、取消或任何写操作。

创建新项目入口：

```text
/webhook/novel-project-new
```

这个页面只展示创建表单；真正创建仍提交到：

```text
POST /webhook/novel-project-create
```

浏览器提交后会返回中文创建结果页。结果页会说明“待生成设定集”表示任务已排队但内容尚未生成，并提供“立即生成设定集”按钮。该按钮提交到 `POST /webhook/novel-generate-bible-now`，会从前端直接调用当前 n8n 配置的 GLM 完成设定集生成，可能需要等待一会儿。

查看小说设定集、大纲、目录、已写章节和项目操作入口：

```text
项目列表 -> 查看控制台
```

直接地址格式：

```text
/webhook/novel-project-detail?project_id=...
```

项目控制台会展示：

- 设定集：来自 `novel_bibles`。
- 扩写设定补丁：来自 `novel_bible_patches`，补丁需要人工确认后才会合并进正式设定集。
- 大纲与目录：来自 `novel_chapter_outlines`。
- 章节正文与版本：来自 `novel_chapters`，正文默认收起，可单章展开，也可用“正文工具条”展开全部或收起全部。
- 审稿报告：来自 `novel_review_reports`。
- 人工审核记录：来自 `novel_human_reviews`。
- 连续性事实：来自 `novel_continuity_facts`。
- 模型调用日志：来自 `novel_ai_runs`。
- 运行日志和失败原因：来自 `novel_generation_jobs`。
- 导出全文 Markdown：只导出当前正式且已批准或已发布的版本。

项目控制台提供前端生成入口和安全项目级操作。

前端生成入口：

- 立即生成设定集：当项目存在 `GENERATE_BIBLE(PENDING)` 时显示，提交到 `POST /webhook/novel-generate-bible-now`。它会领取当前项目的设定集任务、调用 GLM、写入设定集，并自动创建生成大纲任务。前端会标注“立即执行任务”。
- 立即生成扩写设定补丁：当项目存在 `GENERATE_BIBLE_PATCH(PENDING)` 时显示，提交到 `POST /webhook/novel-generate-bible-patch-now`。它会根据扩写计划、当前设定集、已批准正文和事实库生成待确认补丁，不直接改正式设定集。
- 立即生成大纲：当项目存在 `GENERATE_OUTLINE(PENDING)` 时显示，提交到 `POST /webhook/novel-generate-outline-now`。它会领取当前项目的大纲任务、调用 GLM、写入章节目录，并自动创建第 1 章生成任务。前端会标注“立即执行任务”。

安全项目级操作：

- 排队下一步：提交到 `POST /webhook/novel-project-continue`。如果项目还没有设定集，会创建设定集任务；如果已有设定集但没有大纲，会创建大纲任务；如果已有已批准当前章节，会创建下一章生成任务。有待审章节、失败任务或队列仍在推进时会阻止继续写作，避免上下文乱序。注意：排队下一步只补齐缺失队列任务，不直接调用模型；如果页面已经出现“立即生成设定集”或“立即生成大纲”，优先点击对应生成按钮。
- 申请重写此章：只显示在当前正式版本章节上，提交到 `POST /webhook/novel-chapter-rewrite-request`。它只创建 `REWRITE_CHAPTER(PENDING)`，旧正式章节仍保持当前可续写版本；重写新稿生成后还要经过 AI 审稿和人工审核。重复点击不会重复创建任务，也不会重复追加人工审核记录。
- 重新发送审核提醒：只显示在待人工审核章节上，提交到 `POST /webhook/novel-review-remind`。提醒任务只发送审核详情链接，不携带通过、拒绝或重写动作。

注意：项目控制台不提供通过、拒绝、要求重写候选稿、删除版本或取消任务按钮。待审核章节只能跳到审核详情页，真正的审核动作仍然必须在审核详情页通过 POST 表单完成。

项目控制台还提供人工管理操作：

- 编辑设定集：提交到 `POST /webhook/novel-bible-update`。后续生成会读取新的设定集，系统会写入项目操作记录。
- 编辑本章大纲：提交到 `POST /webhook/novel-outline-update`。适合在生成下一章前修正章节目标、冲突点、情绪点和钩子。
- 修改项目目标与扩写计划：提交到 `POST /webhook/novel-project-targets-update`。目标章节数不能小于当前进度；如果填写扩写剧情要求且项目已有设定集，系统会创建 `GENERATE_BIBLE_PATCH(PENDING)`，先生成待确认设定补丁。补丁确认应用后，新增人物、组织势力、地点、关系和剧情约束才进入正式设定集，并被后续大纲、导演台和正文读取。
- 确认/拒绝/重生成扩写设定补丁：提交到 `POST /webhook/novel-bible-patch-action`。确认只合并设定集，不直接改正文；拒绝不会写入正式设定；重生成只重新排队补丁任务。
- 暂停 / 恢复项目：提交到 `POST /webhook/novel-project-status-toggle`。暂停后待处理任务会保留，但队列领取会跳过该项目；恢复后队列可以继续推进。
- 手动编辑正文：提交到 `POST /webhook/novel-chapter-manual-edit`。只创建新的候选版本并进入智能审稿，不覆盖当前正式版本。
- 归档 / 恢复项目：提交到 `POST /webhook/novel-project-archive-toggle`。归档是软删除，会取消待处理任务并让队列跳过该项目；恢复后需手动继续写作。

这些管理操作都会写入：

```text
novel_project_events
```

操作记录会在项目控制台的“项目操作记录”区域展示。正文编辑必须走“候选版本 -> AI 审稿 -> 人工通过”；删除项目当前实现为归档软删除，不做物理删除。

## Phase 20 正文编辑与项目归档

手动编辑正文的安全路径：

```text
当前正式版本
-> POST /webhook/novel-chapter-manual-edit
-> 新候选版本 DRAFT_READY + is_current=false
-> REVIEW_CHAPTER(PENDING)
-> 15 号工作流 AI 审稿
-> NEED_REVIEW
-> 16 号审核中心人工通过
-> APPROVED + is_current=true
```

要点：

- 手动编辑不会直接改当前正式版本。
- 同章如果已有待审候选稿、审稿任务或重写任务，会阻止再次创建人工编辑稿。
- 手动候选稿会复制旧正式版本的同章 ACTIVE AI facts 为 PENDING facts，避免通过后事实库断档。
- 人工通过后，旧同章 AI facts 失效，新候选稿 facts 激活。
- 如果人工编辑改变了关键事实，后续仍建议补充事实库编辑能力；当前阶段先保证事实不断链。

项目归档的安全路径：

```text
项目控制台
-> 输入项目名确认
-> POST /webhook/novel-project-archive-toggle
-> 项目状态 ARCHIVED
-> 待处理任务 CANCELLED
-> 队列领取跳过该项目
```

恢复归档项目不会恢复已取消的旧任务。需要继续写作时，回项目控制台点击“继续写作”，由系统按当前状态补齐下一步任务。

只读队列状态页：

```text
/webhook/novel-queue-status
```

这个页面只用于观察任务，不提供重试、取消、通过、拒绝或要求重写按钮。页面上的项目状态、任务状态、任务类型和调用类型都以中文展示，例如：

```text
待处理
运行中
已成功
已失败
生成设定集
生成大纲
生成章节
智能审稿
重写章节
发送审核提醒
```

如果队列页显示失败任务，先用只读 SQL 排查，不要直接改状态：

```sql
SELECT job_type, status, attempt_count, max_attempts, error_message, updated_at
FROM novel_generation_jobs
WHERE status = 'FAILED'
ORDER BY updated_at DESC;

SELECT run_type, success, duration_ms, error_message, created_at
FROM novel_ai_runs
WHERE success = FALSE
ORDER BY created_at DESC;
```

## Phase 11 只读运行日报

只读运行日报入口：

```text
/webhook/novel-daily-report
```

运行日报用于观察当天队列和模型调用情况，不提供重试、取消、通过、拒绝或要求重写按钮。

页面会展示：

- 今日任务总数、成功数、失败数、取消数。
- 今日模型调用总数、成功数、失败数。
- 当前待处理、运行中、失败任务数量。
- 当前待人工审核章节数量。
- 最近失败任务摘要。
- 当天较慢模型调用。

调度策略建议：

```text
建议每十分钟执行一轮队列。
每轮按顺序执行：生成设定集或扩写设定补丁、生成大纲、导演台规划、生成章节、智能审稿、重写章节、发送审核提醒、自动恢复。
默认禁用外部提醒。
只有确认需要外发提醒时才开启真实提醒。
```

队列执行仍使用已有脚本：

```bash
scripts/run_novel_queue_once.sh
```

定时执行示例：

```cron
*/10 * * * * cd /Users/warrn/study/N8N && scripts/run_novel_queue_once.sh >> /tmp/novel_queue_once.log 2>&1
```

如果只需要观察，不执行队列，打开运行日报和队列状态页即可。

## 真实重写 smoke

真实重写 smoke 用于验证：

```text
NEED_REVIEW
-> POST request_rewrite
-> REWRITE_REQUESTED
-> 17 REWRITE_CHAPTER 真实 GLM
-> 新版本 DRAFT_READY + is_current=false
-> 15 REVIEW_CHAPTER 真实 GLM
-> NEED_REVIEW
-> 17 NOTIFY_REVIEW，建议 NOVEL_DISABLE_SERVERCHAN=true
-> POST approve
-> APPROVED + is_current=true
```

核查 SQL 要点：

```sql
SELECT chapter_no, generation_version, status, is_current, parent_chapter_id
FROM novel_chapters
WHERE project_id = '<project_id>'
ORDER BY chapter_no, generation_version;

SELECT job_type, status, chapter_no, payload->>'remind_status'
FROM novel_generation_jobs
WHERE project_id = '<project_id>'
ORDER BY created_at;

SELECT run_type, success, duration_ms
FROM novel_ai_runs
WHERE project_id = '<project_id>'
ORDER BY created_at;
```

预期：

- 原待审稿变 `REWRITE_REQUESTED + is_current=false`。
- 重写新稿先是 `DRAFT_READY/NEED_REVIEW + is_current=false`。
- 人工通过后新稿变 `APPROVED + is_current=true`。
- 同章旧版本不再 current。
- 旧同章 AI facts 变 `INACTIVE`，新 facts 变 `ACTIVE`。
- 真实 GLM 的 `REWRITE_CHAPTER` 和 `REVIEW_CHAPTER` 都写入 `novel_ai_runs`。

## 故障处理

- n8n CLI 执行失败后先确认 `docker start n8n-video-n8n` 已执行，必要时手动启动。
- `RUNNING` 卡住的任务交给 18 号自动恢复；它会重试未达上限的任务，达上限后按任务类型标记失败。
- 如果成功任务仍显示旧错误，重新导入 Phase 8 后的 workflow；成功标记 SQL 已包含 `error_message = NULL`。
- 如果真实 GLM 返回 schema 外字段，优先在 `n8n/code/novel_parse_glm_json.js` 做收敛，不放宽数据库 CHECK。
